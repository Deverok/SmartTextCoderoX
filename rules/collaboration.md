# 协作、提交与评审规则

> 依据：规格 §10.4、§11.5、§12。目标是让人类用户随时能判断"现在做到哪、凭什么说做完了"。

## 1. 分支与提交

| 项 | 规则 |
|---|---|
| 分支 | `feat/<ms>-<slug>`、`fix/<slug>`、`docs/<slug>`、`chore/<slug>`；**禁止**直接推送 `main` |
| 提交信息 | `<type>(<scope>): <what> — <why>`；type ∈ `feat/fix/docs/test/refactor/chore/perf` |
| 粒度 | 一次提交只做一件事；契约变更与实现变更**分开提交** |
| 关联 | 提交信息包含任务 ID 与 `ACC-*` 编号（如 `feat(codebook): 实现 CB-* 校验 — ACC-M1-04`） |
| 禁止 | 提交密钥、`runs/`、真实研究数据、`data/` 下非 `_example` 内容 |

## 2. 契约（Schema）变更流程

1. 新增/修改 `config/schema/*.json`，**递增 `schema_version`**。
2. 提供迁移脚本（`script/maintenance/migrate_schema`）与迁移说明（`docs/dev/migrations.md`）。
3. 更新所有消费方的读取代码与测试（含契约正/反例）。
4. 在 PR 描述中列出：**破坏性变更点 / 受影响产物 / 迁移命令**。
5. 未经此流程，**禁止**让实现假设新字段已存在。

## 3. 每个 PR 必须包含

- [ ] 变更说明（做了什么、为什么、影响范围）
- [ ] **验收证据**：命令 + 测试名 + 结果（规格 §12 的硬门槛）
- [ ] 质量门全绿（`rules/code-structure.md` 第 8 节 / `AGENTS.md` 第 4 节）
- [ ] `CHANGELOG.md` 条目（Keep a Changelog 格式）
- [ ] 若涉及契约：迁移脚本与版本号
- [ ] 若涉及提示词/skills/编码规则：golden 指标对比（变更前后）

## 4. 评审清单（Reviewer 视角，逐条勾选）

**正确性**
- [ ] 契约先于实现，且有失败用例
- [ ] 幂等与往返测试存在且通过
- [ ] 边界与退化情形有覆盖（空数据、极偏分布、缺失、超长、非法值）

**合规性**
- [ ] 无 `rules/forbidden.md` 的红线（尤其 A 类数据红线）
- [ ] 无硬编码；配置有 Schema 校验且 fail-fast
- [ ] 无静默降级/静默默认；降级均带 flag 与日志

**可复现**
- [ ] manifest 必填项齐备
- [ ] 随机行为有种子且记录
- [ ] 产物路径遵循 `{version}/{run_id}`

**可维护**
- [ ] 依赖方向未破坏（`analytics` 不依赖 `agents`）
- [ ] 新增依赖有理由与许可声明
- [ ] 文档已更新（用户手册/开发文档/错误码表）

## 5. 需求变更流程

1. 任何需求疑问或缺口 → **停下来**，在交付回复的【未决与风险】中提出。
2. 由用户决定：修改规格 → 版本升版（v2.4 → v2.5）→ 同步 `stcx-bootstrap/` 中的派生规则 → 再继续开发。
3. **禁止**开发者在代码注释、PR 描述或界面里"顺手"定义需求。

## 6. 交付回复模板（每次任务结束必用）

```
【做了什么】
1. <文件/模块：改动要点>
2. ...

【证据】
- 命令：
- 结果：
- 产物与哈希：

【未决与风险】
- 默认假设：
- 未验证项：
- 需要用户决策：

【下一步建议】
1. ...
```

## 7. 里程碑收尾产物

- `docs/dev/progress/MSx-验收报告.md`：MSx 全部 `ACC-*` 的通过情况、证据、未通过原因、遗留风险。
- 里程碑验收必须逐条对照规格 §12；**不允许**用"功能已实现"替代证据。

## 8. 沟通风格

- **结论先行**：先说做完没做完、结论是什么，再展开。
- 不夸大：未验证就说未验证；不确定就标"待实测"。
- 主动暴露问题：发现问题越早越好；发现问题不报是最严重的失误之一（见 `rules/forbidden.md` D 类）。
